  • • 结果： 创小宝APP（应用程序）服务10000+兼职代理人，触达250万+客户；项目业务新增保费13亿元、内容采纳率28%。这包含业务、产品和运营共同贡献，不等同算法独立增量。
  • • 迁移： 共同问题是将模糊用户诉求拆成可执行任务；研发工具还需补上代码版本、测试环境、数据权限和可回滚执行。

项目三：实时数字人——支撑性能工程【经历】

  • • 背景/目标： 满足实时交互、可打断、长视频生成；普通离线生成方式不能直接满足要求。
  • • 过程/职责： 视频基座后训练，加入音频/文本/关键点控制；TaylorFlow＋DMD（分布匹配蒸馏）实现NFE=4（函数评估次数）；Causal DiT（因果扩散Transformer）和分块生成支持流式交互。
  • • 难点： 蒸馏速度/质量权衡，训练与推理分布对齐，跨块稳定性；选一条讲清模型改动和验证方法，避免同时铺满术语。
  • • 结果： 单卡H100耗时400ms生成550ms视频，支持2min+生成。该计算片段对应实时因子约0.73，仅说明生成计算快于片段时长，不含网络/音频输入/排队/播放的端到端时延，也不能证明高并发。
  • • 迁移： 先明确质量与延迟约束，定位瓶颈，再选择模型/系统优化；不把视频步数蒸馏当作文本投机解码。

Q2：为什么拆12种意图？识别错了怎么办？

  • • 【经历】12种意图来自项目业务能力划分；具体分类表、标注和路由方式需要本人回忆。
  • • 【方案】按任务差异和工具/输出约束拆分；定义多意图、缺参数、域外请求与歧义，不强行每次单标签命中。
  • • 先比较规则/小模型/LLM（大语言模型）路由基线；用混淆矩阵和关键意图召回判断，模型自报置信度不等于校准概率。
  • • 低置信/高风险时澄清、收紧工具或交回人工。问“你们当时怎么做”时只回答真实版本，不沿用此建议冒充过去。

Q3：知识库和记忆有什么区别，效果如何验证？

  • • 【经历】有多模态知识库与上下文记忆；分块、向量库、Reranker（重排序模型）和保留周期未在V4列明。

  • • 知识更新靠入库/索引与有效期；用户偏好不覆盖官方规则。用正确版本命中、证据支持率、过期信息率及撤销后可见性测试验证。

研发工具系统设计

白板题：设计一个研发知识与问题定位助手【推演题／方案】

开头先问： 服务软件/固件/芯片中的哪类研发人员？首个高频任务是什么？输入是文档、代码、日志还是测试结果？允许读什么、改什么？模型和算力可用性如何？这几点未知时，把下面方案标成假设。

以“帮助研发人员根据问题单、代码与日志定位问题、生成有证据的建议”为练习场景，不表示公司实际在做此项目。

用户与任务入口
  → 身份/项目权限与数据分级
  → 任务编排：检索 → 证据整理 → 假设 → 工具验证 → 结论
  → 工具适配：文档/代码/问题单/日志（先只读）
  → 输出：引用、相关版本、验证结果、未知项
  → 可选受控写操作：隔离环境产生补丁 → 测试 → 人工审查
横向底座：模型网关、任务状态、预算、观测、评测、审计

5分钟讲法： 30秒澄清任务，60秒架构，90秒数据和执行链，60秒评测/安全，60秒取舍与试点。被打断时先回答当前问题，不抢着讲完架构。

六个必须能落地的设计点

  1. 数据与版本： 文档按项目、产品、版本、有效时间和权限入库；代码保留仓库、提交、路径、符号与依赖；日志保留环境和时间。不要把不同固件版本的结论拼接。
  2. 执行路径： 先让受控流程完成确定性步骤，开放步骤才交给模型选工具；缺关键信息先澄清，证据冲突时并列展示并请求验证。
  3. 工具契约： 输入输出使用Schema（结构约束），明确类型、错误码、权限和副作用；工具返回原始证据与来源，模型不能把失败的工具调用说成成功。
  4. 状态与恢复： 保存任务目标、版本、计划、证据引用、工具结果、预算、审批和执行标识；关键步骤落检查点。外部写操作单独做幂等/状态查询，恢复执行仍可能重复触发副作用。
  5. 执行边界： 先只读接入；代码执行在临时隔离环境，限制网络、密钥、文件与资源；写问题单、提交补丁或触及设备需独立授权，测试通过后仍由人审查，不自动合并或发布。
  6. 验收与试点： 与研发专家共建真实任务集，先运行低风险高频任务；确认成功率、返工、净节时、安全和成本后扩展。没有基线不许诺“提升30%”。

设计题追问快答

追问60秒回答骨架
一定要多Agent吗？先单编排器＋工具；只有子任务可独立并行、上下文需隔离或角色评测有实际收益时拆分；比较同预算下最终正确率与时延，防止多轮互相强化错误
怎么防止死循环？最大步数/时间/费用；相同工具参数指纹去重；观察状态是否推进；瞬时错误限次重试，权限/参数/逻辑错误走修正或人工；终止条件写在代码层
如何保证不越权？接入身份→检索和工具执行前都授权→结果回传前复核→缓存与日志同样隔离；仅提示词或生成后删敏感词不足
如何防止文档提示注入？文档/代码/日志当证据，不能下发系统指令；工具白名单、参数校验、最低权限和审批在模型外；检测只是辅助，剩余风险靠隔离与可观测控制
框架选什么？稳定流程用普通代码/工作流即可；复杂状态、恢复和人工介入可评估LangGraph；模型API（应用接口）/检索/业务适配分离，避免业务逻辑全部绑在框架内
如何上生产？固定模型/提示/工具/索引版本→离线回归→影子或小流量→人工审查→监测→快速回滚；索引版本需与权限撤销联动

Agent与RAG核心题

以下均为【推演题／方案】。技术原则参考S1–S3；每题先60–90秒回答，追问再展开。

Q6：Workflow、Agent、ReAct分别是什么？

  • • Workflow（工作流）由代码预定路径；Agent由模型根据状态与反馈动态选择动作。企业系统常把开放推理嵌在受控流程里。
  • • ReAct（推理与行动交替）是模型提出动作、工具执行、观察结果再决策的模式；不要求保存或暴露模型的私有思维链，可记录结构化计划、动作依据与工具证据。
  • • 任务可穷举、顺序稳定、要求严格时先工作流；信息不足需探索时有限开放Agent。多Agent（多智能体）增加协调、上下文和成本负担，需用实测收益证明。

Q7：RAG（检索增强生成）为什么检索不到？

  • • 先查正确文档是否入库、版本与权限是否正确，再看切块和查询是否丢信息。研发文档和代码有缩写、符号、版本号，纯语义检索可能不够。
  • • 可组合BM25（关键词检索）与向量检索，按权限和项目版本限制候选，再重排；代码考虑符号/依赖检索，日志考虑时间与错误码。
  • • 分别测Recall@k（前k召回）、重排后证据覆盖、最终回答的引用支持和任务完成率；k、分块长度和模型选择由任务验证，不套万能参数。
  • • 追问“召回高为何答案差”：可能有干扰证据、版本冲突、上下文过长或模型错误使用证据，继续分层诊断。

Q8：RAG、SFT和工具调用如何选择？

  • • RAG更新可查证的知识；Tool Calling（工具调用）读取实时状态或执行操作；SFT（监督微调）改善稳定任务的行为/格式/领域表达，不能替代授权或实时事实。
  • • 先做提示＋检索/工具基线，记录失败分布；只有可靠标注、足够样本和可重复收益时训练。训练集按时间/项目切分，防代码近重复泄漏到测试集。
  • • 【经历边界】本人有视频基座SFT/LoRA（低秩适配）经验；不声称已有文本LLM完整后训练、RLHF（人类反馈强化学习）或Agentic RL（智能体强化学习）的生产经验。

Q9：Context Engineering和Memory怎么设计？

  • • Context Engineering（上下文工程）决定当前模型调用该看到什么：目标/规则、相关证据、工具定义、必要历史、结构化状态；每部分分配Token（词元）预算。
  • • 短期状态与长期知识分开，摘要保留来源和未解问题；长输出用工件引用替代不断复制。摘要可能遗漏证据或改变含义，需要可回看原文。
  • • 长期记忆须有命名空间、访问范围、有效期、更正/删除和冲突策略；不要把推测自动写成用户或产品事实。撤权后也要失效缓存。

Q10：MCP解决了什么？用了就安全了吗？

  • • MCP（模型上下文协议）用于统一工具与资源等能力的交互接口，能降低工具适配成本；具体能力取决于协议版本与服务实现。
  • • 它不自动完成业务权限、工具真实性、数据分级、审计和审批。服务端和执行边界仍需独立鉴权与授权，不把模型选择工具当作权限授予。
  • • 【经历边界】除非本人确实实现过，不声称营销Agent已用MCP；本题为接口治理知识准备。

Q11：如何评估代码/研发Agent，而不被“看起来合理”骗过？

  • • 建真实任务与可验收终态：代码是否编译、已有与隐藏测试是否通过、需求是否满足、是否引入回归；测试不能完全证明业务正确，需要领域专家和代码审查。
  • • 同时查看轨迹：是否读错版本、乱调用、越权、改测试掩盖问题；评测环境隔离，不能将真实机密仓库外传。
  • • 固定预算后测单次成功率，并对同任务多次重复检查稳定性。pass@k（k次中至少一次成功）与pass^k（k次全成功）回答不同问题，不能混作可靠性结论。
  • • LLM-as-a-Judge（模型裁判）适合部分语义判断，应校准人评、随机化顺序、避免自评偏好；最终环境结果与确定性检查优先。参考S3。

Q12：如何证明研发提效？

  • • 先问任务和人群，用完成同类任务的净用时/返工/质量建立基线；净节时须扣审查、纠错和维护摊销，不能用生成Token数或采用率代替效率。
  • • 可做随机或交叉试点，控制任务难度和学习效应；不宜随机时使用匹配任务与前后比较并说明因果限制。
  • • 看团队采用、最终交付周期、缺陷逃逸和每个成功任务成本；跟踪长尾任务，避免只看最佳演示。
  • • 【经历边界】营销内容28%采纳率只属于原项目，研发工具效率从新基线测，不移植该比例。

推理与Transformer基础

以下均为【推演题／知识复习】，来自截图JD与通用模型基础；方案理解与生产经历分开。vLLM（推理框架）调优参考S4，完整基础可继续用既有教材。

Q13：从输入到输出讲一次Decoder-only Transformer

  • • 文本先Tokenizer（词元化），变成ID（编号），查Embedding（嵌入）得到隐藏状态；每层进行注意力和FFN（前馈网络）变换，并通过残差连接传递信息。
  • • 许多现代模型使用Pre-Norm（前置归一化）、RMSNorm（均方根归一化）和SwiGLU（门控前馈）；这属于常见实现，具体模型须确认，不能说所有Transformer都一样。
  • • 注意力用Q/K/V（查询/键/值）投影。简式为softmax(QK^T / sqrt(d_head) + causal_mask) V；因果掩码使当前位置看不到未来。随后拼接多个头并做输出投影。
  • • RoPE（旋转位置编码）常在Q/K上按位置施加旋转，使点积体现相对位置信息；不等同把一个可学习位置向量直接加到V上。
  • • 最终归一化后映射到词表，得到下一Token的logits（未归一化分数）；训练计算损失，生成则按策略选Token并继续。这里描述文本自回归模型，不直接等同视频DiT。

Q14：MHA、GQA、MQA及KV缓存的区别？

  • • MHA（多头注意力）各查询头有对应K/V头；GQA（分组查询注意力）多个查询头共享一组K/V；MQA（多查询注意力）所有查询头共享一组K/V。减少KV头可降低缓存和带宽压力，质量须看训练与模型配置。
  • • 自回归生成时，过去Token的每层K/V在相同上下文和模型下可复用；当前查询随新Token计算，不需要为未来查询保存旧Q。
  • • KV缓存的粗略大小为2 × 层数 × KV头数 × 头维度 × 累计Token数 × 每元素字节数；批次多请求要累加，另有分块、元数据与对齐开销。
  • • 手算例（假设模型）： 32层、8个KV头、头维128、8192Token、FP16（16位浮点）2字节，缓存约1GiB。不是本岗模型或本人实测；不含权重、激活与框架开销。

Q15：Prefill与Decode各自瓶颈？如何测延迟？

  • • Prefill处理输入上下文并建立KV；Decode通常每步生成一个新Token，读取历史KV。长输入的Prefill常有较强计算压力，小批量Decode常受显存带宽约束，实际取决于批量、长度、硬件和并行策略。
  • • TTFT（首Token延迟）从请求进入服务到首Token可见；TPOT/ITL（每输出Token时间/相邻Token间隔）看解码体验；E2E（端到端）还包含完整输出和工具链时长。
  • • P50/P90/P99（延迟分位数）、成功率、吞吐、显存、输入/输出长度与并发要一起报告；单用户Tokens/s（每秒词元数）不能当多用户总吞吐。
  • • 先拆排队、检索、Prefill、Decode、工具等待，再找瓶颈；设定延迟目标后比较吞吐，避免把离线最大批量当交互最佳配置。

Q16：PagedAttention和FlashAttention是不是一回事？

  • • PagedAttention（分页注意力）代表将KV以块进行管理和访问的思路，降低连续内存分配与碎片约束，提高可服务并发；不会让每个Token的KV存储量自动消失。
  • • FlashAttention（高效注意力）通过分块、融合和在线Softmax（归一化）减少GPU高带宽显存与片上存储之间的数据搬运，避免物化完整注意力矩阵；标准密集注意力的算术复杂度没有因此变线性。
  • • 两者解决的层次不同，可以配合；vLLM官网的Paged Attention旧内核说明标为历史文档，面试不背成当前实现事实。

Q17：连续批处理、前缀缓存、分块预填充如何取舍？

  • • Continuous Batching（连续批处理）按调度步让请求进出批次，减少等待最慢请求；更高并发仍会增加排队与显存压力。
  • • Prefix Cache（前缀缓存）复用一致前缀的KV以减少重复Prefill，依赖相同模型/Token/上下文条件；系统提示相似不等于可命中。跨租户缓存须考虑隔离和侧信道风险。
  • • Chunked Prefill（分块预填充）把长输入拆成小块，和Decode调度平衡；小Token预算可能改善ITL、延后长请求首Token，大预算可能改善Prefill效率、拖慢解码。以真实负载看曲线，参数默认值随版本变。

Q18：量化、投机解码和并行，怎么选？

  • • Quantization（量化）区分权重、激活和KV，INT4（4位整数）权重不代表KV也4位；先测精度与任务通过率，再看显存和目标硬件内核是否真加速。
  • • Speculative Decoding（投机解码）由便宜提议方生成候选，目标模型并行验证；收益取决于接受率、草稿成本、批量与硬件。满足正确校正条件时可保持目标采样分布，不能笼统说所有变体都完全无损。
  • • Tensor Parallel（张量并行）拆分张量/权重，省单卡内存但增加通信；Pipeline Parallel（流水线并行）按层切分，有流水空泡与调度成本。先确认单卡是否装得下，再用负载验证扩卡收益。
  • • 【经历兜底】我的性能实战主要来自人脸部署和视频生成，尚无已确认的vLLM架构改造或CUDA/Triton（GPU算子工具）内核生产履历；可以把瓶颈分析方法迁移，但不会把熟悉概念说成做过内核。

Q19：SFT、LoRA、DPO和PPO怎么区分？

  • • SFT用示范输入输出做监督学习，自回归文本常按右移标签计算下一Token交叉熵，训练时能并行计算各位置，仍用因果掩码。LoRA是低秩参数适配方法，常冻结原权重，学习ΔW=BA；它不是单独的数据目标，也不等于完整预训练。
  • • DPO（直接偏好优化）用偏好对和参考策略约束优化相对偏好；PPO（近端策略优化）是可用于基于奖励的策略训练的方法。训练数据、奖励、采样与稳定性要求不同，不能用“都微调”混讲。
  • • 【经历】本人在视频生成基座上用数字人数据做SFT或LoRA；图像/视频建模目标与文本下一Token目标不同。DPO/PPO只讲理解，缺少实际项目就直说。

Q20：多模态模型与视频生成模型如何联系研发工具？

  • • 视觉编码器提取图像/视频特征，经连接模块与语言模型交互是常见VLM（视觉语言模型）路线，细节取决于具体架构；不同模型可能使用跨注意力或不同融合方式。
  • • 对截图、报告图表、界面和波形等资料，可考虑多模态检索/理解；这只是候选场景，先问数据与任务，不假设本团队已有该需求。
  • • 多模态理解不保证数值/坐标精确，也不自动完成电路或存储故障判断；关键结论由确定性工具和领域专家验证。DiT负责生成建模，不能直接当NAND物理机制模型。

高风险：数字与归因

原句/数字可能追问防御口径
13亿元新增保费算法贡献多少？增量如何认定？项目支持的业务结果，不能全归因算法。统计窗口和归因方法未在V4写明，按真实口径补；没有因果实验就不声称独立增量
10000+、250万+、28%活跃/累计？去重？分母？代理人数、客户触达和内容采纳分别报告，不能互换；未核对原始统计前不补去重/活跃窗口，也不称“任务成功28%”
H100 400ms/550ms、2min+并发、分辨率、首帧？生成计算片段，不含完整链路；2min+是持续生成能力，不代表固定耗时生成整段。规格和并发未核对，不报端到端SLA（服务目标）
T4 QPS>200、活体防御>98%和LLM吞吐可比吗？仅限金融活体服务；防御率是在95%真人通过率工作点，不能混用。模型、输入和负载不同，不跨任务比较

中风险：职责与真实性

  • • 6–8人：算法团队规模，路线、任务拆解和推进有证据；招聘/绩效等按本人已确认做法分别讲，不自动推出预算权或当前岗位带人。
  • • 框架、向量库、模型版本：V4没有写的名称面前补核；记不清就描述接口和过程，不猜一个流行名字。
  • • WAN2.2-5B/1.3B：保留V4记载；1.3B具体版本/阶段待核，不能将两个配置说成同一已确认模型发布规格。
  • • 推理优化：TensorRT/TVM经验不等于TensorRT-LLM、CUDA内核或大模型集群调度实战。
  • • 辞职与日期：实际9月30日离职来自用户直接说明，V4“至今”保留为旧文本；口头说明真实状态，避免说目前仍在职。

低风险：概念卡顿时

先给概念边界，再给适用约束，最后说熟悉程度。可以说：“原理上我理解是这几步，具体版本的实现细节我需要再核对；我实际负责过的是……”。已知答错时直接修正，不绕回业务数字。

中文数字兜底：“这个统计口径我需要核对原始记录，我先说明测量方式和责任范围，准确数字可以后补。”如临时切英文：I can follow up with exact figures after the interview.（面试后我可以补充准确数字。）

反问与机会核验

优先问3题。 面试时长未知，若仅留5分钟，问第1、2题并压缩第3题；薪资细节可另向HR确认。

  1. 职责与成功指标： “您这边研发工具团队当前最希望AI解决哪两类问题？这个岗位入职前三个月最重要的交付是什么？一面主要聊Agent，但截图JD偏推理框架和算子，实际职责大致如何分配？”
  2. 级别与权限： “这个岗位主要承担核心模块开发、跨项目技术负责人，还是团队管理？技术路线由谁最终决定？我会向您汇报吗，是否有明确团队和招聘/绩效职责？”
  3. 长期方向： “内部工具目前以项目交付、工具采购集成还是核心平台研发为主？如何衡量净研发提效，是否有稳定预算、平台复用目标与技术发展路径？”

有时间再问：现有工具/模型/算力与可使用数据；领域专家如何参与验收；新招或补招及原因；上海具体地址/武汉出差；发布责任、值守、近4周上下班与周末情况。保持询问语气，不把外部旧帖当本团队事实。

面后决策提醒： 用户已确认内部工具团队归属，现有偏好将“AI成本中心/纯内部工具”列为排除项。即使工具产生效率价值，仍需由用户判断是否改变对这一机会的取舍；“有平台”“经理技术好”不自动解除既有偏好。本轮按明确请求完成手册，保留3.4历史暂评及Interview（面试中）状态，不代替用户接受、撤回或改规则。

倒计时训练

10月27日：约3小时，分段练习

  1. 35分钟：真实架构核对。 画一次营销Agent实现，补模型/框架/服务边界、本人代码职责和一次真实取舍；不确定处标待核，不填猜测。
  2. 30分钟：主项目口述。 各录一次90秒和3分钟版本，检查是否每段都能接实现追问；业务数字最多两项。
  3. 35分钟：白板设计。 讲研发问题定位助手；练一次“不给写权限”、一次“允许隔离环境生成补丁”的方案差异。
  4. 35分钟：技术快问。 手算KV缓存，讲清Attention（注意力）、Prefill/Decode、分页/FlashAttention、RAG诊断与Agent状态。
  5. 30分钟：计时模拟。 2分钟介绍、8分钟项目、8分钟设计、7分钟基础、5分钟反问；该时长是练习设置，不是实际面试安排。
  6. 15分钟：只修3个短板。 回听录音，选择答非所问、数字越界、实现含糊各一处修正，结束高强度复习。

时间不足用第1节的一小时压缩版；今晚不建议为了“使用过框架”临时搭Demo（演示）并写进经历。

10月28日：面前轻量复习

  • • 上午用20分钟重画真实架构、20分钟推理快答、10分钟复述一项真实取舍。
  • • 16:15前确认平台/地点、时长与编程要求；若线上，检查会议软件、麦克风、网络和共享屏幕；若线下，按真实地点另排出发时间，不能套线上安排。
  • • 面前15分钟仅看速览和三个反问；17:00面试。随手记录对方实际职责/权限答案，面后补事实与问答，不补编未被问的问题。

模拟题与自检

这些是【推演练习题】，不是真实公司题库。每题口述不超90秒，再允许一层追问。

练习题达标点
你的Agent中哪些步骤需要模型自主决策？说明真实版本；能区分预定工作流与开放探索
28%采纳率下降，你先查什么？核对口径/用户/任务分布，再做路由、知识、生成和产品侧分解，不能武断归因模型
同一个错误码在不同固件版本含义不同怎么办？版本限定检索、来源冲突提示、需要时工具验证；不靠多数回答投票
Agent写代码通过测试就能合并吗？需求/隐藏回归/安全与代码审查，权限和发布控制独立
任务中断后恢复，会重复创建问题单吗？幂等键/状态查询/外部副作用对账；检查点不自动提供外部恰好一次
为什么不直接多Agent？单流程基线、分工收益与协调代价、同预算验证
两种Attention优化分别改变什么？分页管理与数据搬运；不说注意力算术复杂度线性化
模型吞吐提高但用户感觉更慢？排队/批量/长请求、TTFT/ITL/工具等待与P99分别测
你不懂固件，如何在一个月产出？领域专家共定一类任务与验收；从数据/工具接入和只读试点开始
为什么要选你，不选纯后端工程师？真实AI能力边界、评估与性能取舍、产品化和团队推进；承认复杂后端/领域知识需协作

最终核对： 能不看稿画架构；每个“我做了”可定位到真实模块；数字有边界；方案有失败路径；能问出决定岗位级别和方向的3题。缺真实事故/冲突案例属于待补，不用编故事填满。
